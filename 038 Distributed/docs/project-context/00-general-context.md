# Equipment section — общий контекст

## Что это

L-Charge Backoffice — B2B платформа управления инфраструктурой зарядки EV.
Иерархия: **partner → site → unit → charger/connector**.
Площадки преимущественно **off-grid (Type 2)** — работают на собственной генерации, без подключения к внешней сети.

Раздел **Equipment** — мониторинг физического энергооборудования площадки: DC-зарядки, генераторы, BESS, паралеллинг-панели. Задача раздела — операционный триаж: "что требует внимания прямо сейчас", а не просто отображение структуры.

## Оборудование в проекте

- **Zerova DS series** (90–180 кВт) — DC-зарядки, считаются `charger`, живут в `unit`
- **Mesa GV22 PowerCore** — газопоршневой генератор, 650 кВА / 480 В / 60 Гц, NG/пропан, 12 цил., 21.9 л
- **Mesa Mobile** — мобильная версия генератора, может физически перемещаться между площадками
- **BESS** — конкретный вендор не выбран, параметры ориентировочные
- **Paralleling panels** — конкретный вендор не выбран

## Иерархия оборудования (уточнена в ходе обсуждения)

```
Site
├── Units (интегрированные) → Chargers (Zerova DS) → Connectors
└── Distributed systems (микрогриды)
    ├── Paralleling panel (1:1 с системой — см. ниже)
    ├── Gensets (N штук)
    └── BESS (N штук)
```

**Важное решение: Paralleling panel — одна на distributed system.**
Изначально на скриншотах было 3 панели на 2 системы — это была ошибка в тестовых данных. При кардинальности 1:1 Panel ID и System ID описывают один и тот же объект с разных сторон: панель — физический ассет (щит, выключатели, ресурс), система — логическая группировка операционных метрик (шина, источники, резерв).

## Сквозные принципы дизайна

1. **Operational semantics over raw data.** Метрика должна отвечать на "нужно ли действовать", а не просто отображать значение. Reserve/остаток предпочтительнее Load — оба падают к нулю ("пусто = опасно"), но резерв реагирует на деградацию оборудования даже при неизменной нагрузке (опережающий индикатор).

2. **Три класса метрик по скорости изменения:**
   - **Непрерывные** — валидны всегда, в любом режиме (связь, уровни расходников, аварии, накопители)
   - **Защёлкнутые (latched)** — измеряются только в определённом режиме, но вывод остаётся в силе дольше (например, состояние воздушного фильтра после остановки генератора) — должны показываться с отметкой возраста данных
   - **Режимные** — существуют только в конкретном режиме, в других — не "ноль", а "нет данных"

3. **"Неизвестно" ≠ "плохо".** Offline/no data должны визуально и семантически отличаться от реальных неисправностей — иначе выездной ресурс тратится не по адресу.

4. **Physical intuition для техников.** Данные должны учитывать, как реально работает и обслуживается железо (например, физическое положение переключателя Auto/Manual, а не только программный статус).

5. **Групповые метрики ищут отклонение, а не абсолютное значение.** Один нагруженный генератор — это нормально. Один генератор, который несёт заметно меньше нагрузки, чем остальные в группе, при прочих равных — сигнал скрытой деградации (регулятор, AVR), невидимый по каждому ассету отдельно.

6. **Вычисляемые vs паспортные поля.** Некоторые характеристики (например, номинальная мощность генератора) — не статичный атрибут, а функция от конфигурации (класс рейтинга + тип топлива). Их нельзя хранить одним числом.

## Структура карточки ассета (унифицирована для генератора, BESS, панели)

1. **Current state** (live) — операционные поля: режим, ключевые метрики, инциденты, связь. Сюда же — "медленные, но actionable" метрики вроде "часов до ТО".
2. **Details** (паспорт/конфигурация) — ID, название, номинальные характеристики, накопители (моточасы, циклы, износ выключателей), дата добавления.
3. **Technical specifications** (свёрнуто) — справочные данные из спецификации вендора: модели, вес, сертификации, ёмкости расходников, пороговые значения защит. Read-only reference, не для оперативного чтения.
4. Блок принадлежности (Partner / Site / System / Location) + внутренние заметки.

## Трёхуровневая модель настроек (единая для всех типов оборудования)

| Уровень | Кто редактирует | Риск | Примеры |
|---|---|---|---|
| **Platform-level** | Свободно, оператор backoffice | Не влияет на физику | Название, привязки, расписания, пороги алертов |
| **Controller-level** | С подтверждением, ролевой доступ | Меняет операционное поведение | Auto/Manual, droop, load-dependent start/stop, dispatch strategy, окно синхронизации |
| **Protection parameters** | Read-only в веб-интерфейсе | Безопасность людей/оборудования | Уставки защит, thermal runaway protection (BESS — никогда не редактируется удалённо) |

## Открытые вопросы для команды

- Архитектура управления: где физически исполняется синхронизация и dispatch — в контроллере генератора, в панели, в отдельном EMS?
- Panel vs Distributed system: если 1:1 подтверждается — нужно решить, схлопывать ли их в интерфейсе или оставлять раздельными реестрами (операционный vs hardware).
- Наименование: "Distributed system" vs "Micro grid" — встречается по-разному на разных карточках, нужно унифицировать.
- Нужен реальный regmap (карта регистров Modbus) контроллеров генератора/BESS/панели до финализации состава метрик — часть показателей из спецификаций может быть недоступна телеметрически.
- Нужна спецификация на конкретный BESS-вендор — текущие цифры ориентировочные.
